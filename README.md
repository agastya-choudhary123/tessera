# tessera

A bytecode VM for tensor programs, targeting Apple M4. Its ISA has no hidden
cache. Programs move data explicitly between DRAM and a software-managed
scratchpad using asynchronous, tagged DMA, which is how ML accelerators like
Trainium work. The repo includes an assembler, a static verifier, a reference
interpreter, and a JIT that compiles to native AArch64 + SME2.

```
tessera assembly  ->  assembler  ->  verifier  ->  interpreter (reference)
                                              \->  JIT -> AArch64 + SME2
```

The ISA spec is in [isa/ISA.md](isa/ISA.md). [NOTES.md](NOTES.md) has design
notes and a comparison with Trainium.

## Requirements

You need Apple silicon with SME2 (M4 or later) and the Xcode command line
tools.

The M4 has SME2 but not non-streaming SVE. If you compile ordinary C with
`+sme2`, the autovectorizer emits SVE instructions that crash with SIGILL
outside streaming mode. The Makefile only applies that flag to the files that
need it.

## Building

```sh
make            # the tessera binary
make test       # 15 tests: verifier rejections and interpreter/JIT equivalence
make benches    # hardware measurements and the Accelerate baseline
```

## Usage

```sh
python3 tools/gen_matmul_kc.py --kc 128 -J 128 --cbuf 2 -o asm/mm.tsa
./tessera -M 1024 -N 1024 -K 1024 --check --jit -r 7 asm/mm.tsa

./tessera --disasm asm/mm.tsa | head              # bytecode listing
TESSERA_JIT_DUMP=/tmp/jit.bin ./tessera --jit ...  # dump the generated code for objdump
```

`--check` compares the result against a double-precision reference. The
relative error is about 2.1e-7, which is normal f32 rounding.

## Benchmarks

Apple M4 (4 P-cores + 6 E-cores, 16 GB), pinned to a P-core, best of N runs.
`bench/compare.sh` throws away a cold warmup run for each side, because clock
ramp-up costs about 15% on the first run. It then takes the best of three
best-of-seven runs.

**Peak compute.** One P-core's SME unit does 2008 GFLOP/s. A single `fmopa`
is a 16x16 f32 outer product (512 flops) and retires in 0.255 ns. That's 28x
the same core's NEON peak of about 71 GFLOP/s.

**Memory bandwidth** (`bench/memhier`). Only L1 is fast enough to keep up:

| footprint | bandwidth | flops/byte needed for 2008 GFLOP/s |
|---|---|---|
| ≤ 128 KB (L1D) | 327–382 GB/s | 5.3–6.1 |
| ≤ 4 MB (L2) | ~139 GB/s | 14.4 |
| ≤ 24 MB (SLC) | 78–131 GB/s | 15–26 |
| DRAM | 34–70 GB/s | 29–59 |

At the L1 level, a hardware cache uses LRU to decide what stays resident.
For a tiled matmul that's the wrong policy. The panel you need for the next
thousand outer products is the one LRU considers oldest. This is the reason
for an explicitly addressed scratchpad.

**Code generation.** Without data movement (`bench/kloop_u4.tsa`, which runs
outer products on data already in the scratchpad), the JIT sustains 1859
GFLOP/s out of 2008. On the same kernel at 256³, the JIT is 25.6x faster than
the interpreter (729 vs. 28.4 GFLOP/s).

**Data reuse.** Keeping a wider block of B resident lets each packed A panel
be reused across more output tiles. Only one schedule parameter changes here
(M=N=1024, K=128):

| resident B width `Jc` | A-panel reuse | DRAM traffic | GFLOP/s |
|---|---|---|---|
| 32 | 1x | 22.0 MB | 265 |
| 64 | 2x | 13.4 MB | 531 |
| 128 | 4x | 9.0 MB | 818 |

**Compared with Accelerate.** Apple's Accelerate reaches 1430 GFLOP/s on one
thread and only 1707 on 8. That suggests the SME unit is shared between
cores rather than one per core. So single-threaded Accelerate is the fair
comparison for tessera's single compute thread:

| shape | tessera | Accelerate (1 thread) | ratio |
|---|---|---|---|
| 1024³, K=128 | 735 | 1226 | 0.60x |
| 1024³, K=256 | 877 | 1487 | 0.59x |
| 1024³, K=512 | 866 | 1649 | 0.53x |
| 1024³, K=1024 | 855 | 1711 | 0.50x |
| 2048², K=512 | 782 | 1653 | 0.47x |
| 2048², K=1024 | 787 | 1619 | 0.49x |

tessera gets about half of Accelerate's speed, using kernels generated by a
~150-line Python scheduler.

## The verifier

`ts_verify` checks three things before anything runs:

- **V1:** no compute instruction reads or writes DRAM directly.
- **V2:** every scratchpad access is in bounds.
- **V3:** nothing reads scratchpad bytes while a DMA into them is still in
  flight.

V3 is a dataflow analysis over intervals, run to a fixpoint, so it also
catches hazards that span loop iterations. In `tests/bad_loop_carried.tsa`,
the loop body looks correct from top to bottom, but its read races with the
previous iteration's DMA:

```
$ ./tessera tests/bad_loop_carried.tsa
V3 pc=5: reads SPM bytes with a DMA still in flight (missing wait): ldv v0, spm[0]
verification FAILED
```

Bugs like this depend on timing: the kernel works when DMA is slow and
breaks when it's fast. Tile shapes that overflow the scratchpad are also
rejected at compile time.

## Limitations

- Most of the gap to Accelerate is data movement. The scratchpad is 128 KB,
  and the best configuration uses all 131,072 bytes of it. Trainium's
  on-chip SRAM is about 100x larger. NOTES.md goes through the details.
- One compute thread (plus DMA worker threads), f32 only.
- Matmul is the only kernel with a scheduler in `tools/`.

## Layout

```
src/tessera.h    ISA definition: opcodes, address spaces, machine model
src/asm.c        assembler and disassembler
src/verify.c     static verifier (V1–V3)
src/vm.c         reference interpreter, used to check the JIT
src/dma.c        DMA engine: 4 SPSC queues, pack16 and accumulate transforms
src/arm64.h      AArch64 + SME2 instruction encoders
src/jit.c        bytecode to native code (MAP_JIT)
tools/           schedulers that generate tessera assembly
asm/             pre-generated matmul kernels
bench/           hardware measurements and the Accelerate baseline
tests/           correctness tests and programs the verifier must reject
```
